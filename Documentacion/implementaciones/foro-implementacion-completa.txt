RESUMEN EJECUTIVO
================================================================================

Se ha implementado exitosamente un sistema de foros personalizado por carrera
siguiendo las especificaciones del documento "foro detallado.txt". El sistema
incluye seguridad, moderación automatica, restricciones de acceso por carrera,
y multiples tipos de publicaciones.


================================================================================
FUNCIONALIDADES IMPLEMENTADAS
================================================================================

1. FOROS POR CARRERA
   -----------------
   ✓ Cada carrera tiene su propio foro (ej: "Informatica-Point", "Leyes-Point")
   ✓ Campo "carrera" en modelo Foro determina a que estudiantes pertenece
   ✓ Usuarios solo pueden crear posts en el foro de su carrera (campo career)
   ✓ Usuarios pueden comentar en posts de cualquier foro (sin restriccion)
   ✓ Metodo puede_postear(usuario) verifica permisos de creacion
   
   Implementacion:
   - Modelo Foro actualizado con campo de carrera
   - Vista PostListCreateView valida carrera antes de crear post
   - Excepcion PermissionDenied si intenta postear en foro de otra carrera
   - Admins y moderadores pueden postear en cualquier foro


2. TIPOS DE PUBLICACIONES
   -----------------------
   ✓ COMENTARIO: Publicacion estandar con texto
   ✓ ENCUESTA: Publicacion con opciones definidas para votacion
   ✓ IMAGEN: Publicacion con imagen adjunta (requiere revision manual)
   ✓ OTRO: Tipos personalizados adicionales
   
   Implementacion:
   - Enum TipoPost en modelo Post con 4 opciones
   - Campo tipo en Post (CharField con choices)
   - Modelo OpcionEncuesta para opciones de encuestas
   - Modelo VotoEncuesta para registrar votos de usuarios
   - Campo imagen (ImageField) para posts con imagenes
   - Campo imagen_aprobada para control de revision


3. FILTRADO DE CONTENIDO Y CENSURA
   --------------------------------
   ✓ Deteccion automatica de palabras inapropiadas
   ✓ Censura parcial de palabras ofensivas (ej: "mierda" → "m#####")
   ✓ Tres listas de palabras:
     - BANNED_WORDS: palabras prohibidas (envian post a revision)
     - MODERATION_WORDS: palabras que requieren moderacion manual
     - OFFENSIVE_WORDS: palabras censuradas parcialmente
   
   Implementacion:
   - Funcion censurar_texto() con expresiones regulares
   - Sobrescritura de metodo save() en Post y Comentario
   - Censura mantiene primera letra + # para el resto
   - Busqueda case-insensitive con limites de palabra (\b)
   - Aplicada automaticamente antes de guardar en BD


4. REVISION DE IMAGENES
   ----------------------
   ✓ Imagenes van a area de procesamiento especial
   ✓ Solo administradores pueden aprobar/rechazar imagenes
   ✓ Panel de administracion con acciones masivas
   ✓ Posts con imagenes no aprobadas quedan en estado "revision"
   
   Implementacion:
   - Campo imagen_aprobada (BooleanField, default=False)
   - En metodo save() de Post: imagen sin aprobar → estado REVISION
   - Admin de Post con columna "imagen_status" con indicadores visuales
   - Acciones admin: aprobar_imagenes, rechazar_imagenes
   - Filtros en admin por estado de imagen


5. SEGMENTACION Y ROLES DE USUARIO
   --------------------------------
   ✓ Roles: admin, moderator, director_carrera, student
   ✓ Administradores: acceso completo a gestion de foros e imagenes
   ✓ Moderadores: revision de comentarios, sin acceso a panel admin
   ✓ Estudiantes: solo pueden postear en foro de su carrera
   
   Implementacion:
   - Campo role en modelo User (enum Roles)
   - Verificacion de rol en vistas (is_staff, role in ['moderator', ...])
   - Permisos diferenciados en perform_create
   - IsModerator permission class para endpoints de moderacion
   - Panel admin con permisos granulares


6. FORO PUBLICO VS FORO PRIVADO
   -----------------------------
   ✓ Foros publicos: todos pueden ver y comentar
   ✓ Foros privados: solo estudiantes de la carrera pueden ver
   ✓ Admins y moderadores pueden ver todos los foros
   
   Implementacion:
   - Campo es_privado en modelo Foro (BooleanField, default=False)
   - Metodo puede_ver(usuario) verifica acceso
   - Filtro en ForoListView con Q objects:
     Q(es_privado=False) | Q(es_privado=True, carrera=user.career)
   - Serializer incluye campo puede_postear calculado


7. CAMBIO DE CARRERA
   ------------------
   ✓ Estudiantes pueden cambiar de carrera
   ✓ Al cambiar: pierden privilegios del foro anterior
   ✓ Automaticamente se asigna acceso al nuevo foro
   ✓ Historial completo de cambios para auditoria
   
   Implementacion:
   - Metodo cambiar_carrera(nueva_carrera, razon) en modelo User
   - Modelo CambioCarrera para registrar historial
   - Campos: usuario, carrera_anterior, carrera_nueva, razon, fecha_cambio
   - Inline en UserAdmin para ver historial de cambios
   - Admin de CambioCarrera en modo solo-lectura

================================================================================
FLUJO DE USUARIO
================================================================================

CREAR POST:

1. Usuario accede al foro de su carrera
2. Crea post seleccionando tipo (comentario/encuesta/imagen/otro)
3. Si es encuesta: agrega opciones
4. Si es imagen: sube archivo
5. Backend censura texto automaticamente
6. Backend verifica palabras prohibidas
7. Backend verifica que es su foro de carrera
8. Si hay imagen: estado REVISION, espera aprobacion admin
9. Si hay palabras prohibidas: estado REVISION
10. Si todo OK: estado PUBLICADO


COMENTAR EN POST:

1. Usuario puede comentar en cualquier foro (sin restriccion)
2. Backend censura texto automaticamente
3. Comentario se publica inmediatamente


CAMBIAR CARRERA:

1. Usuario solicita cambio (via admin o endpoint futuro)
2. Admin ejecuta user.cambiar_carrera(nueva_carrera, razon)
3. Se crea registro en CambioCarrera
4. Usuario pierde acceso a foro anterior
5. Usuario gana acceso a nuevo foro
6. Mensaje informativo del cambio


================================================================================
ENDPOINTS API
================================================================================

GET /api/foros/
   - Lista foros accesibles para el usuario
   - Filtrado automatico por privacidad
   - Query params: sede, carrera
   - Incluye campo puede_postear

GET /api/posts/?foro_id=X
   - Lista posts de un foro
   - Query params: foro_id, orden (nuevo/top), estado

POST /api/posts/
   - Crea nuevo post
   - Valida que sea foro de su carrera
   - Body: foro, titulo, cuerpo, tipo, [imagen], [anonimo]

POST /api/posts/{id}/comentar/
   - Crea comentario (sin restriccion de carrera)

POST /api/posts/{id}/votar/
   - Vota post (upvote/downvote)

POST /api/posts/{id}/reportar/
   - Reporta post inapropiado

POST /api/posts/{id}/moderar/
   - Modera post (solo moderadores)
   - Body: accion (aprobar/rechazar/ocultar), razon


================================================================================
CASOS DE USO
================================================================================

CASO 1: Estudiante de Informatica crea post en su foro
   1. Usuario con career="Ingenieria en Informatica"
   2. Accede a foro "Informatica-Point"
   3. Crea post tipo "comentario"
   4. Titulo: "Ayuda con Python"
   5. Cuerpo: "Necesito ayuda con este codigo"
   6. Backend valida: carrera OK
   7. Backend censura: sin palabras ofensivas
   8. Post publicado exitosamente

CASO 2: Estudiante de Informatica intenta postear en foro de Leyes
   1. Usuario con career="Ingenieria en Informatica"
   2. Intenta crear post en foro "Leyes-Point"
   3. Backend valida: carrera NO coincide
   4. PermissionDenied: "Solo puedes crear publicaciones en el foro de tu carrera..."
   5. Post rechazado

CASO 3: Estudiante crea encuesta con palabras ofensivas
   1. Usuario crea post tipo "encuesta"
   2. Titulo: "Que piensan de esta mierda?"
   3. Backend censura: "Que piensan de esta m#####?"
   4. Backend detecta palabra ofensiva en texto original
   5. Estado = REVISION
   6. Moderador revisa y decide aprobar/rechazar

CASO 4: Estudiante sube imagen
   1. Usuario crea post tipo "imagen"
   2. Adjunta archivo de imagen
   3. Backend: imagen_aprobada = False
   4. Estado = REVISION
   5. Admin revisa imagen en panel de administracion
   6. Admin aprueba: imagen_aprobada = True, estado = PUBLICADO
   7. Imagen ahora visible para todos

CASO 5: Estudiante cambia de carrera
   1. Usuario con career="Ingenieria en Informatica"
   2. Admin ejecuta: user.cambiar_carrera("Derecho", "Cambio vocacional")
   3. Se crea registro en CambioCarrera
   4. Usuario ya no puede postear en "Informatica-Point"
   5. Usuario ahora puede postear en "Derecho-Point"
   6. Posts anteriores en foro antiguo se mantienen

CASO 6: Usuario comenta en foro de otra carrera
   1. Usuario de Informatica
   2. Lee post interesante en foro de Leyes
   3. Crea comentario (permitido)
   4. Comentario se publica exitosamente
   5. Usuario puede interactuar pero no crear posts
